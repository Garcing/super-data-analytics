# 编排数据分析

## 定位

将用户问题稳定映射到最新、受治理的数据实体，再编排最小必要技能完成任务。准确率首先是上下文、实体解析和验证问题，不是 SQL 生成问题。

本技能只负责：

- 判断轻量回答还是正式分析。
- 识别并消除会改变结果的歧义。
- 强制优先使用语义层解析指标、维度、表和关系。
- 在写 SQL 前形成可执行的 SQL Spec。
- 编排查询、分析、验证和交付。
- 验收结果是否可追溯、可解释、可交付。

具体归因、预测、效果评估、图表和报告方法由对应技能负责，不在这里重复。

## 三类主要风险

执行前检查：

1. **概念与实体歧义**：业务词可能对应多个指标、数据实体、ID、粒度或人群定义。
2. **数据与语义过期**：指标定义、关系、字段或 SQL 文档可能已变化。
3. **检索失败**：正确答案存在，但没有检索到，Agent 转而猜测字段或来源。

不得用“SQL 可以运行”代替口径正确性。

## Phase 0：选择路径

### 直连

以下情况不必进入完整编排：

- 只问指标定义、字段、表、关系或业务上下文 → `retrieving-context`
- 已给出明确 SQL，只要求执行 → `querying-data sql`
- 已给出明确 DAX 或指定 Power BI 模型，只要求执行 → `querying-data powerbi`
- 已提供结果数据，只要求单图 → `visualizing-data`
- 已提供完整结论，只要求生成报告 → `building-reports`
- 模板查询或维护 → `using-templates`

### 编排

以下情况进入本技能：

- 业务问题尚未映射到明确指标或数据实体。
- 请求包含“分析、为什么、看看情况、帮忙看看”等开放意图。
- 涉及多个指标、维度、关系或分析步骤。
- 需要异动归因、预测、效果评估或正式报告。
- 结果将用于汇报、决策或外部分享。

## Phase 1：理解问题并消除歧义

先从用户原话和已有上下文提取：

- 核心问题及要支持的决策
- 指标或待计算概念
- 统计实体与去重键
- 分析对象、人群或业务范围
- 时间范围、时间字段和时区
- 维度、筛选、排除项
- 对比基准
- 期望输出粒度与交付形式

### 实体消歧规则

- “用户、客户、订单、员工、商品、线索”等必须落实到具体业务实体和稳定 ID。
- “人数/个数”必须明确统计对象以及使用哪个键去重。
- 比率必须明确分子、分母各自代表的实体和范围，但不要擅自改写受治理公式。
- 同名概念在不同团队、阶段或表中含义不同，必须确认适用语境。
- 旧名称仍作为数据取值时，展示使用新名称，过滤使用真实存储值。
- 陌生术语先检索业务上下文，不猜。

只有歧义会实质改变结果且无法从受治理来源唯一解析时才追问。一次只问最关键的阻塞问题。若唯一候选足够明确，直接继续并在交付时说明采用的口径。

### 维度解析规则

把用户问题中用于分组、筛选、对比或展示的业务属性都视为待解析维度，不把相似字段或若干枚举值直接当作同一维度。

1. 先检查参与计算表的最新 SQL 输出。只有字段含义与用户所问维度一致时才直接使用；字段名相似、取值部分重合或可以用 `CASE` 凑出分类，都不算已覆盖。
2. 字段不存在或含义不确定时，检索 `维度` 实体，用维度名称、维度组和取值特征识别候选；再取得来源字段、来源表、维度组关联键和维度组主键维度。
3. 用事实表是否提供兼容的关联键判断候选能否接入。必要时沿事实表 SQL 的字段血缘确认别名映射，例如语义字段可能来自物理关联键但使用了中文别名。
4. 若事实表已输出同一受治理维度，使用直接字段；否则按维度元数据把来源表作为维表引入，通过维度组关联键连接。维度补充默认 `LEFT JOIN`，除非受治理元数据或问题中的筛选明确要求缩小事实总体。
5. 多个候选都合理且会改变分组、筛选或结果时才追问；没有候选或缺少可验证关联键时停止，不猜字段、不猜 JOIN、不派生业务分类。

维度实体授权的是该维度来源表及关联键的补充连接，不替代普通事实表之间的 `表关系`。不得把“非 A”自动归为 B，也不得用顺序、名称模式或课程阶段等邻近概念推导另一个受治理维度，除非维度元数据明确给出该映射。

## Phase 2：语义层优先

除用户已提供可直接执行的 SQL/DAX 或现成数据外，查数前必须调用 `retrieving-context`。

### 必需顺序

1. 运行 `schema` 了解当前实体和关系配置。
2. 用 `search` 检索指标、表、表关系和维度；宁可扩大 targets，不要漏掉可能实体。
3. 对命中的指标用 `cypher` 精确取得：
   - 指标 ID、定义和计算说明
   - 计算表达式及指标过滤条件
   - 默认时间字段
   - 参与计算表
   - 启用的表关系
   - 常用维度
4. 对用户实际要求的每个分组或筛选维度，按“维度解析规则”确认直接字段或完整维度契约；常用维度只提供候选，不限制用户使用其他受治理维度。
5. 递归展开表关系的前置链，确认起始表、加入表、JOIN 类型、JOIN 条件和顺序。
6. 对参与计算表和维度来源表读取表名、别名、类型、粒度、主键、说明及可用的 SQL 文档链接。
7. 对 SQL 文档执行：

```bash
node scripts/retrieve.js doc --doc "<Docx URL 或 token>"
```

始终读取最新文档正文，不依赖对话中旧 SQL 副本。

### 来源优先级

1. 已定义且受治理的指标、维度和表关系
2. 受治理的表及其最新 SQL 文档
3. 用户明确提供并确认的 SQL或数据
4. 原始表探索

Power BI 不是默认来源。只有用户明确要求 Power BI、DAX 或指定语义模型时才使用。

### 无覆盖或冲突

- 未找到指标：换业务别名和相邻实体继续检索，再尝试从受治理表构造。
- 多个候选均合理且会改变结果：列出简短差异并请用户确认。
- SQL 文档、图谱字段或关系互相冲突：停止执行，指出冲突；必要时重新同步图谱。
- 受治理来源仍无法支撑问题：说明缺口，不发明表、字段、JOIN 或口径。

## Phase 3：形成 SQL Spec

写 SQL 前形成简短的内部执行契约。只写本次查询实际用到的项，不预填空字段。

```yaml
question:
metric:
  id:
  calculation:
grain: {entity: , key: }
time: {field: , range: }
dimensions:
  - id:
    role: group_by | filter | display
    field:
    join:  # 直接字段时省略；需要补维表时写完整 ON 条件
filters: []
sources:
  - alias:
    table:
    revision:
joins:
  - id:
    type:
    on:
output: {grain: , columns: []}
checks: []
open_questions: []
```

直接维度只写 `field`；补充维度在同一项写 `join`，其来源表列入 `sources`。没有额外 JOIN、检查或未决问题时省略对应块。决策用途、时区、排除项、排序和数量限制仅在会影响结果时补充，不作为固定模板字段。

SQL Spec 不默认展示。出现口径确认、执行失败、高风险交付或用户要求查看时，只展示相关部分。

在进入查询前确认：

- 指标、实体、去重键和粒度一致。
- 时间字段、范围和完整周期含义明确。
- 所有字段均来自参与计算表或已解析维度的来源表。
- 普通表 JOIN 严格来自已启用的关系链；维度补充 JOIN 严格来自维度契约。
- 每个用户要求的分组和筛选维度都已记录直接字段或可验证关联键。
- 所有阻塞歧义已经解决。

## Phase 4：编排执行

### 默认查数链路

```text
retrieving-context → SQL Spec → querying-data sql → 返回结果
```

将每份语义表 SQL 作为对应别名的 CTE 或子查询使用，保留文档中的业务逻辑；只做必要的别名适配和数据库方言调整。按表关系的前置顺序连接，再按 SQL Spec 引入必要的维度来源表，最后应用指标表达式、过滤条件、时间范围和维度。不得在 SQL 编写阶段重新发明维度分类。

### 分析技能

- 异动上涨、下跌、波动、告警 → `diagnosing-anomalies`
- 趋势预测、目标制定、达成判断 → `predicting-trends`
- 活动、实验、产品动作、ROI → `evaluating-impact`
- 确定性单图 → `visualizing-data`
- HTML、Image、Streamlit、飞书报告 → `building-reports`
- 正式高风险成品复核 → `validating-analyses`

常见链路：

```text
异动归因：
retrieving-context → SQL Spec → querying-data sql
→ diagnosing-anomalies → validating-analyses（按风险）→ building-reports

周期报告：
using-templates → retrieving-context → SQL Spec → querying-data sql
→ 对应分析技能 → validating-analyses（按风险）→ building-reports
```

用户提供现成数据时跳过取数，直接进入对应分析或报告技能。

## Phase 5：验证

### 查询前

- 字段和表别名存在。
- JOIN 顺序与语义关系链一致。
- JOIN 两侧字段类型和业务含义兼容。
- 维度字段、来源表和关联键与 SQL Spec 一致，没有用 `CASE` 或邻近字段替代受治理维度。
- 维度来源表在关联键上的唯一性足以保持目标粒度。
- 聚合没有因一对多关系改变目标粒度。
- 过滤条件、排除项和时间范围完整。

### 查询后

至少检查：

- 是否成功返回，行数和列是否符合预期。
- 结果是否为空或异常全零。
- 关键字段的 NULL、重复和时间覆盖。
- 聚合结果是否满足适用的业务常识或数学约束。
- 数据最大日期或其他新鲜度信号是否支持所问时间范围。

查询结果可疑时先诊断，不直接包装成业务结论。正式汇报、因果判断或高影响决策按需调用 `validating-analyses`；普通查数不强制增加高成本审查。

## Phase 6：交付

轻量回答至少说明：

- 结果
- 指标或计算口径
- 时间范围与主要过滤条件
- 来源层级：受治理指标、受治理表、用户 SQL/数据或原始探索
- 影响可信度的数据缺口

正式分析还应：

- 区分事实、推断和建议。
- 让关键结论可追溯到查询和来源。
- 说明数据新鲜度与必要限制。
- 返回实际生成的文件或链接。

不默认倾倒完整 SQL Spec 或长 SQL。用户要求审阅、复跑或留档时，保存并返回实际执行 SQL。

## 连续追问

复用已经确认的指标、实体、时间范围、SQL Spec 和结果。只有新问题改变了指标、实体、人群、时间、粒度或口径时，才重新对齐受影响部分。
