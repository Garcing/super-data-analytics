# 对齐数据需求

## 概览

识别用户数据分析类意图，引导用户将模糊想法转化为标准需求文档，明确业务场景、分析目的、指标口径和字段范围等；并按照核心流程指引，编排和使用 `super-data-analysis` 系列SKILL套件完成任务

## 应用场景

`数据运营`、`数据科学家`、`数据分析师` 等数据类岗位，日常工作中涉及的一切场景，比如提取/清洗数据，挖掘业务洞察、制作数据报告、监控数据异常、分析波动归因等

## 触发示例

契合上述应用场景时，用户可能产生的一切与数据分析相关的问题，提问角色可简单分为业务人员和数据分析师

| 用户角色   | 问题内容                             | 提问意图         |
| ---------- | ------------------------------------ | ---------------- |
| 销售人员   | 了解xx人员/团队本月的流水是多少      | 简单查数问数     |
| 主管/经理  | 这个指标的定义是什么？在哪个看板上面 | 了解业务背景信息 |
| 主管/经理  | 这个月业绩下滑的原因是什么           | 数据波动归因     |
| 组长       | 帮我整理一份团队业绩排名报表         | 查数+数据整理    |
| 数据分析师 | 帮我把这个生成数据分析报告           | 生成可视化报告   |
| 数据分析师 | 这个表的字段有哪些，可以关联什么表   | 了解数据资产     |

## 核心流程

你的核心流程是 **对齐需求** 和 **编排技能**，但也存在简单任务下跳过此技能的情况

### Phase0：判断跳过

当识别用户意图为以下情况，可以跳过此技能，直接调用相应技能来完成任务，**避免简单场景变重**

- [ ] 用户只是想查询业务上下文，比如查询某个指标定义，查询有什么数据表（调用 `retrieving-business-context` ）
- [ ] 用户对数据报告模板做增删改查的管理（调用 `leveraging-report-templates` )
- [ ] 用户提供SQL代码/DAX语句，简单跑一下数据（调用 `querying-data-via-powerbi` 或 `querying-data-via-sql` )
- [ ] 用户提供现成数据，在此基础上挖掘洞察/可视化（调用 `mining-business-insights` 或 `generating-insights-report` ）
- [ ] 用户提供现成的数据分析结论，需要生成可视化报告（调用 `generating-insights-report` )
- [ ] 用户明确调用 `super-data-analysis` 系列套件技能



### Phase1：对齐需求

以用户提问内容为起点，调用 `retrieving-business-context` 获取更多上下文信息，填充以下需求模板

如用户提到数据播报/报告模板/分析框架，或特定报告模板名称，调用 `leveraging-report-templates` 匹配对应模板，并直接参考模板内容，跳到Phase2即可

#### 需求模板

##### a. 业务场景

描述这次分析的业务背景，为什么要做这个分析

> 是否必须：否，但如果要进行深入的数据分析洞察，建议追问用户
>
> 追问示例：这个数据需求是在什么业务背景下产生的？

| 案例                                                         |
| ------------------------------------------------------------ |
| 最近两周我们上线了新的注册引导流程，但发现新用户的次日留存率有所下降，需要排查是哪个环节导致了流失 |
| 用户投诉率已经连续两周提升了，需要了解投诉原因的占比变化，看看是哪类投诉导致的波动 |
| 本月份的营收规模环比上涨了30%，老板需要了解增长点发生在哪个环节，对整个业务链路做一次复盘 |

##### b. 核心分析目标

明确你希望通过这次分析解决什么具体问题，或者支持什么业务决策

> 是否必须：否，但如果要进行深入的数据分析洞察，建议追问用户
>
> 追问示例：这个数据需求的核心分析目标是什么？

| 案例                                                         |
| ------------------------------------------------------------ |
| 评估A/B测试中新UI对转化率的影响，以决定是否将新UI全量上线    |
| 找到导致投诉率上升的主要投诉原因，以尽快发现客诉风险予以解决 |
| 发现总结业务增长的机会点，将其沉淀复用放大                   |

##### c. 指标定义

分析基于指标来呈现，必须有足够清晰的指标定义和数据来源；通常存在两种情况，用户明确提出需要的指标，或用户提出一个分析场景，再通过上下文定位合适的指标

> 是否必须：是，当指标不存在时需追问
>
> 追问示例：
>
> ①你提到的指标<xxx>不存在，是否是指以下几个相似指标？
>
> ②暂时没有指标支持这个数据需求，请联系数据分析同事补充

通过调用  `retrieving-business-context` 完成以下指标卡片，目前尚未支持SQL取数，必须定位取数的PowerBI数据看板，并获得对应的语义模型ID

| 指标名称 | 指标定义   | 数据看板名称 | 语义模型ID   |
| -------- | ---------- | ------------ | ------------ |
| <指标1>  | <业务含义> | <数据看板>   | <语义模型ID> |
| <指标2>  | <业务含义> | <数据看板>   | <语义模型ID> |

##### d. 数据范围与维度

确定数据的时间范围或样本范围来定位分析对象，确定有效的维度来实现数据的上探下钻

> 是否必须：否，若未提供，时间范围酌情选择本月/近30天/近一周等；维度则非取数必要条件，直接返回指标结果

通过调用  `retrieving-business-context` 完成数据维度+范围卡片，以下为示例

| 维度名称 | 是否用作数据范围 | 数据范围说明 | 维度定义   |
| -------- | ---------------- | ------------ | ---------- |
| 日期     | 是               | 近三个月     | <维度定义> |
| 城市等级 | 否               |              | <维度定义> |

##### e. 交付形式

从 文本 / 图片 / pdf / web / 飞书文档 中明确一个或多个交付形式

> 是否必须：否，若未说明，默认文字形式即可

以下是几种交付形式的补充说明

| 交付形式 | 补充说明                                                     |
| -------- | ------------------------------------------------------------ |
| 文本     | 直接返回文字结果，可以包含emoji, 表格或markdow格式           |
| 图片     | 将分析结论通过图片形式呈现，调用 `generating-insights-report` 并声明图片 |
| pdf      | 将分析结论以pdf文件形式程序，调用 `generating-insights-report` 并声明pdf |
| web      | 将分析结论以pdf文件形式程序，调用 `generating-insights-report` 并声明web |
| 飞书文档 | 将分析结论呈现在飞书文档，调用 lark- 系列SKILL实现           |

### Phase2：编排技能

使用SKILL套件完成数据分析需求，基本流程是取数-分析-可视化

取数：取决于是否提供SQL代码，若有则通过 `querying-data-via-sql` 执行，否则正常走 `querying-data-via-powerbi`

```text
需求一：新注册引导流程用户次日留存下降分析
querying-data-via-powerbi 获取注册用户数、次日留存率、APP使用时长等指标，mining-business-insights 对比新版和旧版注册流程的留存率是否存在显著差异，generating-insights-report 生成可视化web报告

需求二：本月投诉率上升波动归因分析
querying-data-via-powerbi 获取订单数、订单投诉工单数等指标，diagnosing-anomaly 选择异动归因拆解方法，mining-business-insights 挖掘出上升最大贡献的投诉原因，generating-insights-report 生成可视化图片报告

需求三：下个月收入目标制定
querying-data-via-powerbi 获取历史收入月度序列，predicting_trends 选择轻量预测方法并回测，输出保守/基准/挑战三档目标，visualizing-data 生成预测趋势图
```



### Phase3：答疑改进

在初始需求不明确情况下，数据分析结论通常不会一次解决所有疑惑，用户会继续提出新的疑问，你需要继续补充完善需求文档，进行需求总结—分析交付—内容补充—继续总结的循环，直到用户没有产生新的疑问，数据需求得到满足。
