# 对齐数据需求

## 技能定位

本技能是 `super-data-analysis` 系列的入口路由器。它不只是收集需求，而是负责判断用户的数据分析请求应该走轻量回答、上下文检索、取数、洞察分析、报告生成，还是多技能组合流程。

核心目标：

- 将模糊的数据想法转化为可执行分析任务。
- 避免简单问题被复杂化。
- 确保指标、时间、维度、来源和交付物足够清楚。
- 在来源不可用或口径不明确时及时说明缺口。
- 编排最小必要技能集合完成任务。

## 运行环境与依赖

本技能是纯方法论路由，无脚本、无第三方 Node/Python 依赖，也不直接读取环境变量。它编排的具体技能各自负责安装依赖和读取 `~/.super-data-analytics/config.json`。


## 适用范围

当用户问题涉及以下内容时，优先考虑本技能：

- 查数问数：某个指标、团队、人员、区域、产品在某时间范围内的表现。
- 指标解释：指标定义、口径、来源看板、语义模型、相关维度。
- 数据资产理解：表、字段、维度、可关联数据、看板位置。
- 异动归因：指标上涨、下跌、波动、异常、转化下降、投诉上升等。
- 业务洞察：从数据中总结机会点、风险点、原因、建议。
- 数据报告：日报、周报、月报、复盘报告、专题分析报告、数据播报。
- 数据可视化：根据数据或结论生成图表、图片、Web、PDF、飞书文档等。

## 技能套件

| 技能 | 何时使用 |
| --- | --- |
| `aligning-requirements` | 当前入口技能。用于意图识别、轻重分流、需求澄清、流程编排和最终验收。 |
| `retrieving-context` | 查询指标定义、业务口径、数据资产、看板、语义模型、字段、维度、业务背景。 |
| `using-templates` | 查询、匹配、复用、维护数据播报、周期报告、复盘报告、专题分析报告模板（CLI：`scripts/templates.js`，子命令 `list/read/create/update/delete`）。 |
| `querying-data` | 统一数据查询入口，按 `--source sql\|powerbi` 路由。适合已有语义模型 ID 或可写 SQL 的指标取数。 |
| `diagnosing-anomalies` | 异动归因方法论。指标上涨、下跌、异常波动、口径差异、同比环比变化、监控告警后的原因诊断与贡献度拆解。 |
| `predicting_trends` | 趋势预测和目标制定方法论。下月/下季度预测、目标设定、趋势外推、达成判断、资源预算预估。 |
| `evaluating-impact` | 效果评估与实验检验方法论。产品上线、运营活动、Push、发券、投放、A/B 实验、DID 试点的有效性、ROI、是否全量/加码判断。 |
| `visualizing-data` | 把结构化数据生成确定性单图 PNG/SVG，适合报告插图、文档图表、PPT/PDF 图表素材，数值必须准确时优先于 AI 生图。 |
| `building-reports` | 将分析结果生成 HTML / Image / Streamlit / 飞书 等格式报告交付物（按格式路由）。 |
| `validating-analyses` | 分析成品交付前的独立质检：复算关键数字、查分析陷阱、图表诚实性、给置信度评级（可发布 / 带说明发布 / 需修订）。 |
| `lark-doc` / `lark-slides` 等飞书技能 | 当用户要求飞书文档、幻灯片等飞书交付时使用；通常由 `building-reports` 生成内容后再交给对应飞书技能落地。 |

## 总体运行原则

1. 先判断任务轻重，再决定是否进入完整需求对齐。
2. 只追问会阻塞执行的问题，不把每个字段都变成问卷。
3. 先确认来源和口径，再做结论。
4. 当来源冲突时，说明冲突并选择更权威来源。
5. 当必需来源不可用时，不硬编数据结论，改为说明缺口并请求替代材料。
6. 每次只选择最小必要技能集合，避免重复调用和流程过重。
7. 正式交付物必须经过结果验收，不能只停留在“已生成”的口头说明。

## Phase 0：意图识别与轻重分流

先判断用户问题属于哪种响应模式。

### inline：轻量回答

适合直接在聊天中回答，通常不需要完整需求模板。

使用场景：

- 查询一个指标定义、字段含义、表关系或看板位置。
- 用户给出 SQL/DAX，只要求执行并返回结果。
- 用户提供现成数据，只要求简单汇总、排序、对比或画图。
- 用户询问某个报告模板是否存在，或管理模板。
- 用户明确只要文字答案、表格答案或一次性图表。

处理方式：

- 指标/表/业务上下文问题：调用 `retrieving-context`。
- 模板问题：调用 `using-templates`。
- SQL 取数：调用 `querying-data --source sql`。
- PowerBI/DAX 取数：调用 `querying-data --source powerbi`。
- 现成数据做异动归因/预测/效果评估：按场景调用 `diagnosing-anomalies` / `predicting_trends` / `evaluating-impact`。
- 现成数据画确定性单图：调用 `visualizing-data`。
- 现成结论需要生成报告：调用 `building-reports`。
- 能直接完成时不要进入完整 Phase 1。

### report：正式分析或交付

适合进入完整需求对齐和多技能编排。

使用场景：

- 异动归因、复盘分析、专题分析、业务洞察。
- 需要解释原因、拆解贡献、输出建议。
- 需要生成图片、PDF、Web、飞书文档等正式交付物。
- 用户的问题依赖多个指标、多个维度或多个数据源。
- 用户希望得到可复用、可转发、可汇报的分析结果。

处理方式：

- 进入 Phase 1 对齐需求。
- 根据来源和交付形式编排 Phase 2。
- 结束前执行 Phase 3 交付验收。

## Phase 1：按需对齐需求

不要机械追问所有字段。先从用户原话、业务上下文和可用模板中补全，只有缺失项会影响执行时才追问。

### 1. 业务场景

说明这次分析发生在什么业务背景下，为什么要做。

是否必须：否。深入归因、复盘、策略建议类任务建议补充。

可追问：

```text
这个分析是为了解决什么业务问题，还是用于某次汇报/复盘？
```

### 2. 核心分析目标

明确这次分析要回答什么问题，支持什么决策。

是否必须：复杂分析必须明确；简单查数可省略。

可追问：

```text
你希望最终回答的是“发生了什么”“为什么发生”“影响多大”，还是“接下来怎么做”？
```

### 3. 指标口径

明确指标名称、定义、聚合方式、数据来源和可查询位置。

是否必须：涉及指标取数、对比、归因、报告时必须。

处理规则：

- 如果用户已明确指标，调用 `retrieving-context` 校验定义、看板和语义模型。
- 如果用户只描述业务问题，先用 `retrieving-context` 找候选指标。
- 如果指标不存在或口径不清，必须追问或说明当前无法可靠取数。
- 如果存在多个相似指标，列出候选项让用户确认。

指标卡片：

| 字段 | 内容 |
| --- | --- |
| 指标名称 | 用户指定或上下文检索出的指标 |
| 指标定义 | 业务含义、计算口径、聚合方式 |
| 权威来源 | 看板、语义模型、数据表、文档或用户提供数据 |
| 查询方式 | PowerBI、SQL、用户数据、其他 |
| 注意事项 | 过滤条件、延迟、排除项、已知口径差异 |

### 4. 数据范围与维度

确定分析对象、时间范围、过滤条件和拆解维度。

是否必须：时间范围通常必须；维度可按任务需要补充。

默认规则：

- 用户未说明时间范围，优先按业务语境选择：本月、近 7 天、近 30 天、上周、上月。
- 异动分析必须有基准期和观察期。
- 排名类问题必须确认排名对象和排序指标。
- 漏斗/转化类问题必须确认漏斗步骤和人群范围。

维度卡片：

| 字段 | 内容 |
| --- | --- |
| 时间范围 | 例如本月、近 30 天、2026-05-01 至 2026-05-31 |
| 分析对象 | 人员、团队、产品、城市、渠道、客户、用户群等 |
| 拆解维度 | 日期、地区、渠道、商品、老师、班级、客诉原因等 |
| 过滤条件 | 是否排除测试数据、无效订单、内部账号等 |
| 对比基准 | 环比、同比、上线前后、实验组/对照组等 |

### 5. 交付形式

明确最终输出形态。

默认：未说明时直接以聊天文字、表格或图表返回。

| 交付形式 | 处理方式 |
| --- | --- |
| 文本 | 直接返回分析结论、表格、Markdown。 |
| 单张确定性图表（PNG/SVG） | 调用 `visualizing-data`。 |
| HTML / Image / Streamlit 报告 | 调用 `building-reports` 按格式路由。 |
| 飞书文档 / 幻灯片 | 调用 `building-reports`（lark 格式）形成内容，再交给 `lark-doc` / `lark-slides` 落地。 |
| 飞书消息 | 生成摘要后调用对应飞书消息技能发送。 |

## Phase 2：来源发现、权威性判断与降级

在取数或分析前，先判断这次任务需要哪些来源，以及哪个来源最权威。

### 来源优先级

按任务类型选择权威来源：

- 指标定义：优先 `retrieving-context` 中的指标定义、业务口径和权威文档。
- 指标数值：优先 PowerBI 语义模型或被确认的 SQL 查询结果。
- 数据资产：优先业务知识图谱、表结构、字段说明、数据资产文档。
- 报告结构：优先 `using-templates` 中已沉淀模板。
- 用户提供现成数据：在当前任务内视为主要证据，但要说明数据来自用户提供。
- 用户提供结论：可用于报告生成，但不能当作已验证数据事实，除非用户明确说明已审阅。

### 来源冲突处理

如果不同来源给出不同定义或结果：

1. 不要直接混用。
2. 说明冲突在哪里。
3. 优先选择更接近事实来源的材料。
4. 如果无法判断权威来源，要求用户确认。

示例：

```text
我查到“投诉率”在看板 A 和文档 B 中口径不同：A 使用订单投诉数/订单数，B 使用投诉用户数/下单用户数。后续分析需要先确认采用哪个口径。
```

### 来源不可用时的处理

如果必需来源不可用：

- 停止依赖该来源的结论。
- 告诉用户缺少什么。
- 请求用户提供替代材料，如 SQL、导出表、截图、指标口径、语义模型 ID。
- 可以继续做不依赖该来源的部分，例如需求整理、分析框架、报告大纲。

如果缺失来源只是辅助信息：

- 继续使用现有证据。
- 在最终结论中标注“缺少某来源，结论可能受影响”。

## Phase 3：技能编排

根据任务类型选择最小必要技能集合。

### 基础路由规则

- 只问指标定义、看板、字段、表：`retrieving-context`
- 查询或维护报告模板：`using-templates`
- 用户提供 SQL：`querying-data --source sql`
- 用户提供 DAX 或明确 PowerBI 语义模型：`querying-data --source powerbi`
- 已有数据，需要异动归因 / 趋势预测 / 效果评估：按场景选 `diagnosing-anomalies` / `predicting_trends` / `evaluating-impact`
- 需要把结构化数据画成确定性单图：`visualizing-data`
- 已有结论或数据，需要正式报告：`building-reports`
- 需要飞书交付：先用 `building-reports` 生成内容，再交给 `lark-doc` / `lark-slides` 等飞书技能

### 常见组合

#### 简单查数

```text
retrieving-context -> querying-data --source powerbi -> 返回结果
```

适合：本月流水、某团队业绩、某指标当前值。

#### 指标解释

```text
retrieving-context -> 返回定义/来源/维度/注意事项
```

适合：指标定义、数据表位置、看板位置。

#### 异动归因

```text
retrieving-context -> querying-data（--source powerbi 或 sql）-> diagnosing-anomalies -> building-reports
```

适合：业绩下滑、投诉率上升、留存下降、转化波动。

#### 周期报告或数据播报

```text
using-templates -> retrieving-context -> querying-data（--source powerbi 或 sql）-> 按场景选 diagnosing-anomalies / predicting_trends / evaluating-impact -> building-reports
```

适合：日报、周报、月报、经营分析、复盘报告。

#### 用户提供现成数据

```text
按场景选 diagnosing-anomalies / predicting_trends / evaluating-impact -> building-reports
```

适合：用户粘贴表格、上传数据结果、给出已跑好的查询结果。

#### 用户提供现成结论

```text
building-reports
```

适合：把结论整理成 Web、PDF、图片、飞书文档。

## Phase 4：分析执行要求

执行分析时保持以下标准：

- 保留关键 SQL、DAX、查询条件或用户提供数据摘要，方便追溯。
- 明确时间范围、筛选条件和聚合粒度。
- 对归因类问题区分“事实”“推断”“建议”。
- 对排名类问题说明排序指标和是否存在并列。
- 对趋势类问题说明基准期和观察期。
- 对可视化输出确保图表类型匹配问题：趋势用折线，排名用柱状或表格，构成用堆叠/占比，分布用直方图或箱线图。
- 不要为了生成漂亮图表而改变数据口径。

## Phase 5：交付验收

在结束前检查任务是否真正完成。正式对外交付的高风险分析（汇报、复盘、对外分享、因果结论），交付前可调用 `validating-analyses` 做一次独立成品质检，重点抓口径漂移、计算不可复算、分析陷阱和图表误导，并拿到置信度评级。

### inline 验收

直接回答类任务至少包含：

- 结果或结论。
- 指标口径或数据来源。
- 时间范围和过滤条件。
- 如有缺口，说明缺口。

### report 验收

报告或正式交付类任务至少检查：

- 是否使用了用户要求的交付形式。
- 文件、链接或图片是否生成成功。
- 报告中图表是否与数据一致。
- 关键结论是否能追溯到数据或来源。
- 是否说明了口径、时间范围和数据缺口。
- 如果某个必需步骤失败，明确说明失败原因和可替代下一步。

不要只回复“已完成”。如果生成了文件或链接，必须返回可访问路径或链接。

## Phase 6：连续追问与迭代

数据分析经常不是一次完成。用户继续追问时：

- 判断新问题是补充需求、复查口径、追加维度、修改交付形式，还是要求进一步归因。
- 复用已有需求、数据来源和分析结果，不要从零开始。
- 如果新问题改变了指标、时间范围或人群，重新确认受影响部分。
- 将新的结论补充到原有分析上下文中，形成“需求总结 -> 分析交付 -> 内容补充 -> 再总结”的循环。

## 最小需求摘要格式

当任务进入正式分析或报告模式时，先在内部形成如下摘要；必要时可向用户展示简版确认。

```md
## 数据需求摘要

- 业务场景：
- 核心问题：
- 指标口径：
- 权威来源：
- 时间范围：
- 分析对象：
- 拆解维度：
- 对比基准：
- 交付形式：
- 已知缺口：
- 拟调用技能：
```

如果以上字段中只有少量缺失且不阻塞执行，可以直接采用合理默认值并在最终结果中说明。

## 典型示例

### 示例 1：简单查数

用户：查一下华东团队本月流水。

处理：

```text
retrieving-context 确认“流水”指标定义和 PowerBI 语义模型
querying-data --source powerbi 查询华东团队本月流水
inline 返回数值、时间范围、口径
```

### 示例 2：指标解释

用户：这个投诉率是怎么算的？在哪个看板？

处理：

```text
retrieving-context 查询指标定义、看板、语义模型、相关维度
inline 返回定义和来源
```

### 示例 3：异动归因

用户：这个月业绩为什么下滑？

处理：

```text
对齐时间范围、指标口径、分析对象和交付形式
retrieving-context 确认业绩指标和相关维度
querying-data（--source powerbi 或 sql）取数
diagnosing-anomalies 做贡献拆解和归因
building-reports 生成报告
```

### 示例 4：已有数据生成报告

用户：这是我整理好的数据，帮我生成一份 Web 分析报告。

处理：

```text
跳过取数
按场景选 diagnosing-anomalies / predicting_trends / evaluating-impact 基于用户数据总结洞察
building-reports 生成 Web 报告
返回报告路径或链接，并说明数据来自用户提供
```

## 写作风格

- 面向业务用户时，少讲工具过程，多讲结论、口径、来源和下一步。
- 面向数据分析师时，可以保留 SQL、字段、模型、维度和验证细节。
- 对不确定结论使用“可能”“初步看”“需要进一步验证”，不要假装确定。
- 对已验证结果使用清晰、直接的表达。
- 不输出内部思考，只输出用户需要理解和决策的信息。
