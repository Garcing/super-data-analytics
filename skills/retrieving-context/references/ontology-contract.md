# SDA 语义层契约

本参考描述最新版语义层的稳定结构，不保存具体业务数值。具体实体、字段和值始终通过 `retrieve_schema`、`retrieve_search` 和 `retrieve_cypher` 获取。

## 当前实体导航

| 实体 | 解决的问题 | 关键属性 |
|---|---|---|
| 业务线 | 公司/品牌级业务背景 | 名称、说明、经营模式、公司名称 |
| 业务板块 | 业务线下的经营领域 | 名称、所属业务线、说明 |
| 业务小点 | 板块下的具体业务动作 | 名称、所属板块、说明 |
| 数据看板 | 已治理看板与 Power BI 模型定位 | 名称、平台、介绍、语义模型 ID |
| 报告模板 | 报告类型与模板正文入口 | 类型、名称、介绍、URL 链接 |
| 指标 | 指标的权威业务与计算定义 | 名称/ID、定义、计算说明、分子/分母、默认时间字段、过滤、参与表、使用表关系、常用维度组 |
| 维度组 | 同类维度的挂载与下钻契约 | 名称、组说明、组内主键维度、组关联键 |
| 维度 | 分组、筛选和展示字段契约 | 名称/ID、来源表/字段、说明、取值特征、所属维度组 |
| 表 | 数据资产及其实现方式 | 实现方式、表名/中文名/说明/类型/别名、SQL 文档、粒度、主键 |
| 表关系 | 两张或多张表的受治理 JOIN | 关系 ID、说明、参与表、参与表别名、关联基数、JOIN 表达式 |

实体会随运行时配置演进；`retrieve_schema` 返回什么就按什么写 Cypher，不把本表当硬编码白名单。

## 指标到 SQL 的映射

按以下顺序收集契约：

1. 用名称、ID、业务别名搜索指标。
2. 读取指标定义、计算说明、分子/分母表达式、过滤条件和默认时间字段。
3. 解析 `参与计算表`。每张表再取得实现方式、表别名、粒度、主键和 SQL 文档。
4. 解析 `使用表关系` 中列出的关系 ID。直接读取对应“表关系”实体的参与表、基数和 JOIN 表达式。
5. 解析用户需要的维度。`常用维度组` 是发现入口，不是允许列表。
6. 把上述信息交给 querying-data 形成查询规格并执行。

### 直接关系模型

最新版模型的概念映射如下（不是可直接照抄的 Cypher 关系类型；实际边名以 `retrieve_schema` 为准）：

```text
指标 --使用--> 表
指标 --使用--> 表关系
指标 --常用维度--> 维度组
维度组 --包含--> 维度
表关系 --描述--> 参与表 + 别名 + 基数 + JOIN 表达式
```

不存在单独的“表关系链”实体，也不存在“前置关系”“起始于”“加入”“启用链”的递归协议。一个指标使用多条关系时，按参与表依赖和 JOIN 表达式形成可执行顺序；无法唯一排序时先检查表别名和关系覆盖，仍有歧义则停止确认，不自行发明中间关系。

### 基数检查

- `1:1`：仍核对两侧业务键是否真的唯一。
- `1:N`：先确认目标统计粒度；聚合右表或使用 distinct，避免放大。
- 多表关系（如 `1:N:1`）：逐步核对每次 JOIN 前后的行数和主实体去重数。
- 关系元数据授权的是该 JOIN，不代表任意指标都应使用它；仍以指标的 `使用表关系` 为准。

## 表的两种实现

### 逻辑语义表

识别条件：`实现方式 = sql_query`。

- `表名称` 是受治理逻辑名，不保证数据库存在同名 relation。
- `表别名` 是组装指标表达式和 JOIN 的稳定引用。
- `SQL文档` 指向最新查询定义；用 `retrieve_doc_read` 获取正文。
- 在查询中将正文包装为 `<表别名> AS (...)` 的 CTE 或等价派生表。
- 保留文档中的业务逻辑，只做必要方言和别名适配。

### 物理表

识别条件：`实现方式 = physical_table` 或运行时定义的其他物理实现。

- 图谱说明业务用途、类型、别名、粒度和主键。
- 数据库真实列和类型用 `sql_schema` 复核。
- 不因为两个表字段同名就自行建立 JOIN。

## 维度解析契约

对每个 group/filter/display 维度确认：

| 项目 | 判断 |
|---|---|
| 语义身份 | 维度名称、ID、维度组是否对应用户概念 |
| 直接字段 | 参与表是否已输出语义一致的字段 |
| 来源 | 未直接输出时，来源表和来源字段是什么 |
| 关联能力 | 事实表是否有维度组实体上的组关联键；维表主键是否唯一 |
| 取值 | 取值特征是否与用户表达一致 |
| 粒度影响 | JOIN 后是否保持目标统计粒度 |

同名维度 ID 可以出现在不同来源表中；选择来源时同时看表、字段说明、时间有效性和关联键。拉链表必须按生效/失效时间约束，不能只按实体 ID 连接。

## 报告模板

模板由两部分组成：

1. “报告模板”实体：类型、名称、介绍、URL。
2. docx 正文：章节结构、填写约定和示例，通过文档工具读取。

发现模板后先判断其类型是否符合交付场景，再读正文。占位符或测试模板不应被当成正式业务模板。模板只规定呈现结构，不覆盖受治理指标口径。

## 来源优先级

1. 受治理指标、维度、表关系。
2. 受治理表及最新 SQL 文档。
3. 用户明确提供并确认的 SQL 或数据。
4. 原始表探索。

Power BI 看板或语义模型只有在用户明确要求 Power BI/DAX，或当前任务明确以该看板为准时进入对应分支；“看板、KPI、报表”这些词本身不改变默认 SQL 路径。

## 漂移和冲突

- 本地下载的工作簿是审阅快照，不是运行时查询源。
- 工作簿、图谱 schema、SQL 文档三者不一致时，先标记冲突和时间点；不要选择看起来最合理的一份继续。
- 图谱缺少工作簿已有实体通常是部署/同步漂移；配置更新后执行同步。
- SQL 文档字段与图谱表粒度冲突时停止取数，要求治理负责人修正。
- 不把检索分数低解释为实体不存在；先扩大查询和检查 schema。
