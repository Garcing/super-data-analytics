# 编排数据分析

把业务问题稳定映射到最新数据实体，再选择完成任务所需的最小技能集合。准确率首先是上下文、实体解析和验证问题，不是 SQL 生成问题。

本技能只负责路由、对齐和验收；具体取数、归因、预测、实验、图表和报告方法由对应技能负责。

## 三类主要风险

1. **概念与实体歧义**：同一个业务词可能对应不同指标、ID、粒度、人群或时间口径。
2. **语义与数据陈旧**：指标定义、SQL 文档、字段或部署状态可能已变化。
3. **检索失败**：正确答案存在，但没有被搜索到，随后被错误猜测替代。

不得用“SQL 能运行”代替口径正确，也不得用一个看起来合理的结果掩盖未解析的实体。

## 路径选择

### 直连

- 只问定义、表、维度、关系、业务层级或模板 → retrieving-context。
- 已给明确 SQL/DAX，只要执行 → querying-data。
- 已给结构化数据，只要归因/预测/评估/单图 → 对应分析技能或 visualizing-data。
- 已给完整结论，只要发布 → building-reports。

受治理指标即使走直连，取数前仍先用 retrieving-context 确认权威定义。

### 编排

- 请求尚未映射到唯一指标或数据实体。
- 包含“分析、为什么、看看情况、帮忙看看”等开放意图。
- 涉及多个指标、维度、关系、来源或分析阶段。
- 需要归因、预测、效果评估或正式报告。
- 输出将用于高影响决策、管理汇报或外部分享。

简单问题不强行走全链路；每一步都必须对答案产生实际价值。

## Phase 1：理解问题

从用户原话和已有上下文提取：

- 要回答的问题以及它支持的决策。
- 指标或待计算概念、统计实体与去重键。
- 业务范围、人群、渠道、产品或组织。
- 时间范围、时间字段、粒度、时区、完整周期含义。
- 分组/筛选维度、排除项、对比基准。
- 交付形式和受众。

只有缺失项会实质改变结果且无法从受治理来源唯一解析时才追问。一次只问最关键的阻塞问题；唯一候选足够明确时继续，并在交付中写明采用口径。

### 实体消歧

- “用户、客户、订单、员工、商品、线索”等落实到稳定业务 ID。
- “人数/个数”明确统计对象和去重键。
- 比率明确分子与分母各自的实体、范围和时间，但不擅自改写受治理公式。
- 同名词在不同团队或阶段含义不同，比较候选的定义、业务归属和过滤条件。
- 陌生术语先检索；旧名称如果仍是数据值，展示可用新名称，过滤必须使用真实存储值。

### 维度消歧

所有 group/filter/display 属性都要解析：

1. 参与计算表已输出语义一致字段时直接用。
2. 未输出时，从语义层获取维度来源表、字段、关联键、主键维度和取值特征。
3. 只有事实表具备兼容关联键时才能补维表；默认 `LEFT JOIN`。
4. 名称相似、枚举重合或 `CASE` 凑分类不等于受治理维度。
5. 无法验证关联键时停止，不猜字段或 JOIN。

## Phase 2：语义层优先

除用户已给可直接执行的 SQL/DAX 或现成数据外，查数前调用 retrieving-context：

1. 搜索指标、表、表关系和维度；第一次没命中就换别名并扩大范围。
2. 对指标取得 ID、定义、表达式、过滤、默认时间字段、参与表、直接 `使用表关系` 和常用维度组。
3. 对每个实际需要的维度确认直接字段或完整 JOIN 契约；常用维度只是候选入口。
4. 对每张表取得实现方式、别名、粒度、主键和 SQL 文档链接。
5. `实现方式=sql_query` 时用 `retrieve_doc_read` 获取带 revision 的最新结构化块快照，采用 code 块的逐字 `text` 作为 SQL；不自行序列化 Markdown。
6. 对 `使用表关系` 中的每个关系 ID 读取其参与表、基数与 JOIN 表达式。

最新版语义层没有“表关系链”。不要寻找前置关系或递归启用链。一个指标使用多条直接关系时，只能按关系中的参与表、别名和 JOIN 表达式形成顺序；仍不唯一就停止确认。

来源优先级：受治理指标/维度/表关系 → 受治理表与最新 SQL 文档 → 用户确认的 SQL/数据 → 原始探索。Power BI 只在用户明确要求 Power BI、DAX 或指定模型时使用。

## Phase 3：形成 Query Spec

编排取数前写一份简短内部执行契约；只保留本次实际需要的项：

```yaml
question:
decision:
metric:
  id:
  calculation:
grain: {entity: , key: }
time: {field: , range: , timezone: }
dimensions:
  - id:
    role: group_by | filter | display
    field:
    join:  # 直接字段时省略
filters: []
sources:
  - alias:
    table:
    implementation:
    document:
joins:
  - id:
    cardinality:
    on:
output: {grain: , columns: []}
checks: []
open_questions: []
```

Query Spec 默认不展示；用户要求审阅、出现高风险口径确认或执行失败时展示相关部分。

执行前确认：

- 指标、统计实体、去重键和输出粒度一致。
- 时间字段、范围、时区和完整周期明确。
- 每个维度都有直接字段或可验证 JOIN。
- 普通表 JOIN 来自指标直接引用的受治理表关系；维表 JOIN 来自维度契约。
- 一对多关系不会静默改变统计粒度。
- 阻塞歧义已解决。

## Phase 4：编排执行

默认链路：

```text
retrieving-context → Query Spec → querying-data
→ diagnosing-anomalies | predicting-trends | evaluating-impact
→ visualizing-data → validating-analyses → building-reports
```

按需裁剪：

- 上涨、下跌、波动、告警、贡献 → diagnosing-anomalies。
- 未来值、目标、达成判断、资源预算 → predicting-trends。
- 上线、活动、实验、试点、ROI → evaluating-impact。
- 数值准确的静态单图 → visualizing-data。
- 在线报告或单张视觉报告 → building-reports。
- 决策级成品、意外结论或正式发布 → validating-analyses。

用户已提供现成数据时跳过取数。执行中出现新实体或口径歧义时回到 Phase 2，只补受影响部分。

## Phase 5：验证

查询前：字段/别名存在、JOIN 含义和类型兼容、维表键唯一、过滤与时间范围完整。

查询后至少检查：

- 返回列、行数和粒度是否符合 Query Spec。
- 空结果、异常全零、NULL、重复和时间覆盖。
- JOIN 前后行数与主实体 distinct 数。
- 数据最大日期或其他新鲜度信号能否覆盖用户时间范围。
- 数学约束和业务量级是否合理。

可疑结果先诊断，不包装成业务结论。正式或高风险成品交给 validating-analyses 独立复核。

## Phase 6：交付

轻量回答至少包括：结果、采用口径、时间范围/主要过滤、来源层级、影响可信度的缺口。

正式分析还应：

- 区分已验证事实、推断、建议与未验证项。
- 让关键主张能追溯到查询和来源。
- 说明数据新鲜度与限制。
- 返回实际产物链接或图片，而不是只说“已完成”。

推荐附注：

> 来源：受治理语义层 / 受治理表 / 用户数据 / 原始探索 · 新鲜度：<实际查到的最大日期或未知> · 复核：<完成项> · 未验证：<无或清单>

没有所有者、新鲜度或审查信息时写“未知/未执行”，不要补造。

## 连续追问

复用已经确认的指标、实体、时间范围、Query Spec 和结果。只有新问题改变指标、实体、人群、时间、粒度或口径时，才重新对齐受影响部分。
