# 分析成品质检

这是交付链最后一道独立兜底，不是从头重做分析。目标是验证成品实际做出的主张，而不是它看起来是否精致。

## 核心原则

- 能复算就复算，能追溯就追溯；不能验证就明确写“未验证”。
- 按对决策的影响排序，不为修辞小瑕疵阻断交付。
- 区分已验证事实、推断、caveat 和 blocker。
- 高风险、意外、过于完美或因果性强的结论加倍审查。
- 独立改写验证路径，不用“原 SQL 再跑一遍”自我认证。

## 工具组合

- `retrieve_search`：核对受治理指标/维度/表关系。
- `sql_schema` / `sql_query`：独立复算、抽样、行数/粒度/新鲜度检查。
- `powerbi_schema` / `powerbi_query`：成品明确基于 Power BI 时复核。
- `report_html_get`：取得已发布报告最终 JSON。
- `chart`：需要重建对照图时使用。

各分析域的专属检查仍回对应技能：归因看 diagnosing-anomalies，预测看 predicting-trends，实验看 evaluating-impact。

## 风险分级

- **轻查**：日常播报或低影响内部数字——口径、完整周期、图表、抽 1 个关键数字。
- **标准查**：业务分析/复盘——全部步骤，独立复算头条数字。
- **深查**：高层决策、因果结论、对外披露——关键数字全复算、替代解释、域内方法检查、最终渲染与负责人确认。

## 默认流程

### 1. 清点对象与主张

识别报告、SQL、看板、图表或分析文字要回答的问题、受众/决策、核心主张、头条数字、来源、时间、人群、过滤、对比基准和已声明限制。

逐条确认用户要求的指标都已出现，或明确标为不可得/不适用；静默缺失是问题。

### 2. 检查答题与口径

- 成品回答的是用户真正的问题，还是附近更容易的问题。
- 指标定义、分子/分母、去重键、粒度、人群、过滤、单位、时区、cohort 和比较窗口一致。
- 文案口径、语义层定义和 SQL 实际实现三者一致。
- 因果措辞是否有实验或可信准实验支撑。

口径不清先 `retrieve_search`；存在直接关系时确认使用的是指标引用的“表关系”实体，不检查已废弃的表关系链。

### 3. 检查来源与数据质量

确认来源适合当前决策且足够新：

- as-of / 最大日期、分区和窗口完整性。
- NULL、重复、去重、过滤、异常全零、类别覆盖。
- JOIN 基数、覆盖率和主实体 distinct 数。
- 逻辑语义表是否使用最新 SQL 文档，而非旧副本。
- 原始探索是否被误写成受治理来源。

### 4. 独立复算关键数字

按决策影响选 1–N 个关键数字：

- 从原始分子/分母重算率值。
- 用替代查询结构重算同一结果，例如原查询 JOIN 后聚合，复核时先各表聚合再 JOIN。
- 从组件反推头条总量，如用户数 × 人均收入。
- 抽单日/单组/单实体跟过过滤与 JOIN。
- 对账可信看板、历史报告或财务口径（前提是口径一致）。

记录实际复算 SQL、模型 ID、表或报告 ID，保证可复现。

### 5. 检查通用分析陷阱

- **JOIN 爆炸**：多对多或一对多静默放大 count/sum。
- **幸存者偏差**：只保留当前存在实体，遗漏流失/删除/失败者。
- **不完整周期**：半周/半月与完整周期比较。
- **分母漂移**：eligible 人群在两期或两组变化。
- **平均的平均**：未按组大小加权。
- **时区错配**：日截断不一致。
- **分段选择偏差**：用结果变量定义人群。
- **辛普森悖论、相关当因果、小样本、离群点、多重检验、挑时间段、look-ahead**。
- **基数效应**：小基数增长率夸张但影响量很小。

### 6. 检查域内方法

- 归因：`checks.residual`、warnings、分组互斥完整、贡献与因果措辞。
- 预测：历史完整性、结构断点、warnings、回测误差、区间和置信度是否支持表述。
- A/B：SRM、随机性、MDE/样本量、效果量/CI、护栏、提前停止与多重比较。
- DID：干预前多期平行趋势、对照可比性、同期干扰。
- ROI：增量收益、毛利、退款/蚕食和成本完整性。

### 7. 检查图表与最终渲染

- 图型、排序、单位、标题、标签、图例和精度与数据一致。
- 柱状图截断轴、双轴、比例缩放是否误导且有说明。
- 图表数字与正文/KPI 对得上，方向一致。
- HTML/看板等检查最终渲染态：缺图、空表、裁字、占位符、旧缓存、过期链接。
- 标题不比证据更强，caveat 紧邻所限制的结论。

### 8. 评结论与建议

每条结论都应有可见证据；把替代解释、未验证假设和开放问题分开。推荐不能超出数据和方法能支持的范围。

## 评级

- **可发布**：问题回答正确，方法成立，关键数字已验证或风险低，限制清楚。
- **带说明发布**：方向可用，但假设、限制或未验证项必须显式告知决策方。
- **需修订**：数字、口径、方法、因果、数据质量或渲染存在实质问题，发布前必须改。

blocker 包括：关键数字/分母/JOIN/窗口/人群错误、必要检查未跑、来源不可访问、实验设计失效、渲染坏、负责人确认缺失。caveat 是可随成品一起传达的限制，二者不要混列。

## 输出模板

```markdown
## 质检报告

### 总体评级：[可发布 | 带说明发布 | 需修订]

### 已验证
- [主张/数字]：[验证方法、证据、结果]

### 发现的问题
1. [高/中/低] [问题 + 证据 + 对决策的影响]

### 图表与渲染
- [通过项或问题]

### 必改 blocker
- [修复动作、负责人/所需数据]

### 发布时必须说明的 caveat
- [限制]

### 复现记录
- [SQL / 表 / 模型 ID / 报告 ID / 来源]
```

没有源数据访问时，只能做口径、逻辑、方法和呈现层审查；评级中明确这一限制。

## 修复闭环

质检只定位“问题 + 证据 + 影响 + 建议”：

- 口径/数据错 → retrieving-context / querying-data。
- 归因、预测、实验方法错 → 对应分析技能。
- 图表误导 → visualizing-data。
- 报告结构/渲染错 → building-reports。

修复后重新质检受影响主张；不要在质检报告里悄悄改数后直接放行。
